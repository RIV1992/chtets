# Meaning-map release check

## Scope and decision

The maintainer requested the GitHub package and personal installation be updated before a forthcoming large standards-based report, which will provide a field check. Accordingly, this release uses a small functional comparison now. The previously proposed 24-case, three-language experiment and C2 ablation are deferred; they are not claimed as completed or replaced by an efficacy result.

The check compares public v1.1.1 at `9eeb3bc6d1b7a2efd9f1b32ea1d95c93b4fbc2f8` with the v1.2.0 candidate. Inputs and acceptance rubrics were written and frozen before either writer ran. The eight synthetic requests cover standards applicability, numerical propagation, delivery commitments, shortening conditions, translation, punctuation-only work, intentional ambiguity, and a routine email. Standards are fictional; no real GOST compliance assessment is performed.

## Execution

Two fresh writing agents receive the same task requests and access to only their condition's skill and relevant references. They receive no rubrics, diagnoses, or intended answers. Each agent handles eight requests in a single batch; the cases therefore do not have independent fresh contexts. Model and reasoning settings are inherited in the same host. Exact internal computation, billed tokens, and comparable latency are unavailable. Instruction-read inventories record observed files, not per-case loading cost.

A fresh reviewing agent receives anonymous pairs with alternating order, the original requests, and the frozen rubrics. It must record concrete failures, including missing source scope, fabricated compliance, missed dependent passages, and unnecessary expansion of editing permission. Review correctness and request completion before preference; allow ties. Do not tune wording to maximize a preference score. Preserve raw outputs and judgments.

## Acceptance and limits

Resolve any candidate critical failure before release; retain the initial failure record and use fresh analogous material for a substantive repair. A style preference is not a reason to fail a valid answer. Check routine-task restraint as well as complex-task behavior. The package must pass validation, meaningful packaging tests, and generated-document consistency.

Passing supports a limited functional release for field use. It does not establish improvement over v1.1.1, reliable long-document coverage, standards expertise, external verification accuracy, or human voice fidelity. The author reviews those aspects on actual work. Keep actual project sources and private profiles out of this public record; publish only synthetic cases or material explicitly approved for sharing.

If the map introduces false links, loses conditions, encourages over-editing, or adds work without a useful intervention, narrow its routing or revert the optional procedure. Keep underlying evidence and meaning protections.
